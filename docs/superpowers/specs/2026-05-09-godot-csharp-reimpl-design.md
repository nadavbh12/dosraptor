## 1. Goal & scope

### 1.1 Phase 1 (this spec)

Reimplement Raptor: Call Of The Shadows in Godot 4 + C# such that the resulting game produces **simulation-state output equivalent to the original C version**, given identical input scripts. Visual presentation (sprite art, particle effects, animation easing, HUD style, color palette) is allowed to differ.

The work is intended to be performed primarily by an AI coding agent (Claude Code), with human review at design and PR boundaries. Tests must be hard to circumvent without real implementation.

### 1.2 Phase 2 (out of scope here)

Two-player local & online multiplayer, new mechanics, new content. Phase 2 is explicitly deferred. The architecture chosen here must not foreclose phase 2, but no phase-2 features are designed in this spec.

### 1.3 Non-goals

- Pixel parity with the C version. Visuals are free to modernize.
- Cross-engine portability beyond Godot 4 .NET.
- Console publishing (PS5/Switch/Xbox). Desktop and web export are sufficient.
- Replacing the existing C codebase. The C codebase is preserved as the museum/reference implementation and as the parity ground-truth generator.

### 2.2 What lives where

- `src/Sim/`: gameplay code that affects the parity-checked state. Subject to the strict rules in §4.
- `src/View/`: cosmetic — particle systems, screen shake, animation curves, post-processing. May use `delta`. Cannot mutate sim state.
- `src/UI/`: menus and briefing. Affects sim only via menu state transitions (which are part of parity).
- `assets/`: committed binary artifacts produced by the one-time extractor (§5). Treated as read-only data.
- `tests/parity/`: committed goldens. Regenerated only when the schema changes (rare).

### 2.3 Cross-repo workflow

Regenerate parity goldens (rare, manual):

```bash
# In dosraptor
RAPTOR_PARITY_OUT=/tmp/credits.parity.txt build/raptor.app/Contents/MacOS/raptor
# ... commit /tmp/credits.parity.txt → raptor-godot/tests/parity/scripts/credits.parity.txt
```

`dosraptor` ships a `tests/golden_parity_capture.sh` script that regenerates the full parity corpus and outputs to a directory. The output directory is then copied into `raptor-godot` and committed.

## 3. Engine configuration

### 3.1 Godot version

Godot 4.3 or higher, .NET edition. Locked in `project.godot` and verified in CI. C# target: .NET 8.

### 3.2 Determinism settings

Set once at boot in an autoload script:

```csharp
// src/Sim/SimBootstrap.cs (autoload)
public override void _Ready()
{
    Engine.PhysicsTicksPerSecond = 70;     // matches the original PIT divisor
    Engine.MaxPhysicsStepsPerFrame = 8;    // catch up under load
    Engine.MaxFps = 0;                     // uncapped frame rate
}
```

Test mode (set via `RAPTOR_TEST_FAST=1`):

```csharp
if (OS.GetEnvironment("RAPTOR_TEST_FAST") == "1")
{
    Engine.MaxPhysicsStepsPerFrame = 256;  // run as many ticks per real frame as possible
    AudioServer.SetBusMute(0, true);       // no audio (would gate on real time)
    // Headless mode is enabled at process launch via `godot --headless`,
    // not at runtime; this branch only configures audio + tick budget.
}
```

In `--headless` mode with `MaxFps = 0` and `MaxPhysicsStepsPerFrame = 256`, a 25-second mission completes in 0.2–0.5 s (target: 50× real time).

### 3.3 RNG

Per the original C version, RNG is deterministic and seeded once per wave with `1024 * wave_num`. Reimplement in C# as:

```csharp
// src/Sim/SimRng.cs
public sealed class SimRng
{
    private readonly RandomNumberGenerator _rng = new();
    public void SeedForWave(int waveNum) => _rng.Seed = (ulong)(1024 * waveNum);
    public int Next(int max) => _rng.RandiRange(0, max - 1);  // mirrors random(N)
}
```

One `SimRng` instance is owned by the active wave controller. All sim-affecting randomness goes through this instance. Code review enforces this — `GD.Randi()` / `GD.Randf()` / `Mathf.Randf()` are banned in `src/Sim/`.

The RNG sequence does NOT need to byte-match libc rand() in the C version. Tolerances on parity output (§7) absorb that drift. (See §11 for why this works.)

## 4. Architecture: idiomatic Godot, with discipline

### 4.1 Pattern: idiomatic Node2D entities (Pattern B)

Each game entity is a `Node2D` (or appropriate subclass) with its own state, `_physics_process` updates, and signal-based communication. This is the conventional Godot pattern. Trade-offs analyzed in §12.

```
WaveController : Node              # owns the wave logic, spawns enemies, holds SimRng
├── Player : CharacterBody2D
│   ├── Sprite2D
│   ├── CollisionShape2D
│   └── PlayerInputBuffer
├── Enemies : Node2D               # parent for all enemy nodes
│   └── Enemy : CharacterBody2D    # one per active enemy, one .cs class per type
│       ├── Sprite2D / AnimatedSprite2D
│       ├── CollisionShape2D
│       └── (per-type AI fields)
├── Bullets : Node2D               # parent for all bullets (player + enemy)
│   ├── PlayerBullet : Area2D
│   └── EnemyBullet : Area2D
└── HUD : CanvasLayer
```

### 4.2 The discipline (`delta` ban + tick contract)

These rules apply only to `src/Sim/` (game logic), not `src/View/` (cosmetics):

1. **No `_process(delta)` for sim logic.** All sim updates go through `_physics_process(delta)`. The `delta` argument is named for compatibility but **unused** — sim logic uses tick counters.
2. **No `delta` in motion math.** Movement is `position += velocity_per_tick`, where `velocity_per_tick` is the per-tick integer or fixed-point increment.
3. **No wall-clock time in sim logic.** No `Time.GetUnixTimeFromSystem()`, no `OS.GetTicksMsec()` in `src/Sim/`. Use the global `framecount` counter.
4. **One RNG instance per wave.** All randomness goes through `WaveController.Rng`. No `GD.Randi()` etc. in sim files.
5. **Sim state lives in nodes, not in autoloads.** The exception is the `framecount` counter (`SimClock` autoload).

Enforcement: a CI lint (`scripts/lint_sim.sh`) greps `src/Sim/` for forbidden patterns:

```bash
grep -nE '\b(_process|delta|GD\.Rand|Mathf\.Rand|Time\.|OS\.GetTicks)' src/Sim/**/*.cs && exit 1
```

Whitelisting individual sites is allowed via inline comment `// LINT-OK: <reason>` but treated as a code-review item.

### 4.3 Tick orchestration

A single `SimClock` autoload owns the per-tick lifecycle:

```csharp
public partial class SimClock : Node
{
    public static int Frame { get; private set; }

    public override void _PhysicsProcess(double _) {
        Frame++;
        // emit checkpoint output if RAPTOR_PARITY_OUT is set, every 70 frames
    }
}
```

Order of `_PhysicsProcess` invocation across siblings is Godot-defined (scene-tree order). Sim entities should not depend on cross-entity ordering within a tick. Where ordering matters (e.g., bullet hits applied before enemy AI), use signals deferred to the next frame, or explicit phase separation in WaveController.

### 4.4 Collision

Use `Area2D` with signal-based callbacks (`area_entered` / `body_entered`). Godot's broadphase order is engine-defined but stable per binary. Replay determinism (L1) catches any nondeterminism the engine introduces; if it surfaces, fix by aggregating collisions into a sorted list per tick before applying.

### 4.5 Save format

JSON via `System.Text.Json` (human-readable, easy to inspect during dev). The save schema mirrors the C `PLAYEROBJ` struct field-for-field. Cross-version save compatibility with the C original is **not** required — saves are local to this build. Round-trip equality is enforced by L3 invariants (§11).

## 5. Asset pipeline

### 5.1 One-shot extraction in C

A new tool in `dosraptor/tools/extract_assets/` (single C program reusing `GLB_GetItem`):

```bash
./extract_assets path/to/FILE0000.GLB path/to/FILE0001.GLB output/
# Produces:
#   output/sprites/<NAME>.png      — every PIC item, decoded with the correct palette
#   output/palettes/<NAME>.pal     — every PAL item
#   output/levels/<NAME>.json      — every MAZELEVEL block, JSON-encoded
#   output/sounds/<NAME>.wav       — every PCM patch
#   output/music/<NAME>.mid        — every MIDI item
#   output/text/<NAME>.txt         — every TXT item (briefings, credits, help)
#   output/sprites/<NAME>.meta.json — SPRITE struct (HP, money, AI fields)
#   output/demos/<NAME>.json       — every DEM item, decoded as RECORD[]
```

The output directory is committed to `raptor-godot/assets/`. No GLB at runtime in Godot.

### 5.2 Why one-shot vs runtime GLB reader

Considered a runtime GLB reader in C# but rejected for phase 1: adds ~500 lines of decryption + decode code, slows iteration, and we don't have a use case for runtime asset modding (deferred to phase 2).

### 5.3 Demo extraction

Each `DEM_DEMO[1-3]G[1-3]` GLB item is extracted to JSON:

```json
{
  "header": { "max_play": 1100, "demo_game": 0, "demo_wave": 0 },
  "records": [
    {"frame": 0, "b1":0, "b2":0, "b3":0, "b4":0, "px":160, "py":160, "playerpic":3},
    {"frame": 1, "b1":0, "b2":0, "b3":0, "b4":0, "px":160, "py":159, "playerpic":3},
    ...
  ]
}
```

Godot loads these via `JsonResource` at test time and uses them as ground-truth player trajectories (§6).

## 6. Demo replay implementation

The Godot version implements a `DemoPlayback` mode that mirrors the C `DEMO_Think` function:

```csharp
public partial class DemoPlayback : Node
{
    private DemoRecords _records;
    private int _index;
    
    public override void _PhysicsProcess(double _) {
        if (_index >= _records.records.Length) {
            EndDemo();
            return;
        }
        var r = _records.records[_index++];
        _player.Position = new Vector2I(r.px, r.py);
        _player.PlayerPic = r.playerpic;
        _player.Buttons = (r.b1, r.b2, r.b3, r.b4);
    }
}
```

In demo mode, the player position is **overridden** every tick from the recorded sequence. Enemy AI runs normally with seeded RNG. The output is captured at the standard 1Hz checkpoint rate and compared against the corresponding C-side parity file.

## 7. Test plumbing

### 7.1 Checkpoint format (shared schema)

`tests/parity/schema.json`:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "RaptorParityCheckpoint",
  "type": "object",
  "required": ["fc","win","player_x","player_y","score","shield",
               "enemies","pbullets","ebullets","obj_hash"],
  "properties": {
    "fc":         {"type":"integer", "minimum":0},
    "win":        {"enum":["MENU","BRIEFING","HANGAR","STORE","MISSION_1",
                           "MISSION_2","MISSION_3","CREDITS","HELP","ORDER",
                           "DEATH","LANDING","INTRO","UNKNOWN"]},
    "player_x":   {"type":"integer", "minimum":0, "maximum":319},
    "player_y":   {"type":"integer", "minimum":0, "maximum":199},
    "score":      {"type":"integer", "minimum":0},
    "shield":     {"type":"integer", "minimum":0, "maximum":100},
    "enemies":    {"type":"integer", "minimum":0, "maximum":64},
    "pbullets":   {"type":"integer", "minimum":0, "maximum":64},
    "ebullets":   {"type":"integer", "minimum":0, "maximum":64},
    "obj_hash":   {"type":"string", "pattern":"^[0-9a-f]{16}$"}
  }
}
```

One JSON object per line (NDJSON). `obj_hash` is FNV-1a over the player's inventory state vector for cheap detection of inventory drift.

### 7.2 Capture: C side

A new env var `RAPTOR_PARITY_OUT=path` extends the existing harness:

```c
// In Do_Game's per-frame loop (RAP.C around 1105):
if (g_parity_out && (FRAME_COUNT % 70 == 0)) {
    fprintf(g_parity_out,
        "{\"fc\":%d,\"win\":\"%s\",\"player_x\":%d,\"player_y\":%d,"
        "\"score\":%u,\"shield\":%d,\"enemies\":%d,"
        "\"pbullets\":%d,\"ebullets\":%d,\"obj_hash\":\"%016llx\"}\n",
        FRAME_COUNT, win_state_name(), playerx, playery,
        plr.score, OBJS_GetAmt(S_ENERGY),
        count_enemies(), count_pbullets(), count_ebullets(),
        compute_obj_hash());
}
```

Implementation lives in `dosraptor/port/platform/parity.c` (~80 lines).

### 7.3 Capture: Godot side

Same format, emitted by a `ParityEmitter` node that taps into `SimClock.Frame`:

```csharp
public partial class ParityEmitter : Node
{
    public override void _PhysicsProcess(double _) {
        if (_out == null) return;
        if (SimClock.Frame % 70 != 0) return;
        var entry = new ParityEntry { /* fields */ };
        _out.WriteLine(JsonSerializer.Serialize(entry));
    }
}
```

Activated by `RAPTOR_PARITY_OUT=path` env var, mirroring C side.

### 7.4 Comparator

`tests/comparator/parity_diff.py`:

```
Inputs:
  --c-golden  path/to/scripts/credits.parity.txt
  --godot-out /tmp/godot_credits.parity.txt
  --tolerance tolerances.json

Output:
  PASS / FAIL with first divergent checkpoint

Tolerances (per field):
  fc:        exact (must align frame indices)
  win:       exact (no tolerance — enum)
  player_x:  ±8
  player_y:  ±8
  score:     ±15% AND ±100 absolute (whichever is larger)
  shield:    ±2
  enemies:   ±1
  pbullets:  ±20%
  ebullets:  ±25%
  obj_hash:  exact (advisory only — log mismatches but don't fail)
```

Pass criterion: ≥95% of checkpoints satisfy all tolerances. Below 95% = FAIL.

### 7.5 Headless test runner

`tests/runners/CheckpointRunner.cs`:

```bash
godot --headless --path . --script tests/runners/CheckpointRunner.cs \
    -- --script tests/scripts/credits.txt --out /tmp/godot_credits.parity.txt
```

Loads the script, drives input via simulated `Input.ParseInputEvent`, runs at fast tick, captures parity output.

## 8. Test layers (L1, L2a, L2b, L3, L4, L7)

| Layer | What | Source of truth | Runtime |
|---|---|---|---|
| **L1 — Replay determinism** | 1 short script × 2 fast Godot runs, exact diff | Godot vs itself | <2 s |
| **L2a — Script parity vs C** | 8 scripts × fast Godot, compared to committed C goldens | `tests/parity/scripts/*.parity.txt` | ~5 s |
| **L2b — Demo parity vs C** | 9 demos × fast Godot, compared to C goldens | `tests/parity/demos/*.parity.txt` | ~3 s |
| **L3 — Property invariants** | Assertions during L2 runs | (no external) | $0 |
| **L4 — Seed sweep** | 100 seeds × `mission_start` × fast Godot, compared to C goldens | `tests/parity/seeds/*.parity.txt` | ~50 s |
| **L7 — AI visual diff** | ~50 paired screenshots, vision-LLM judged | C-side captures + Godot captures | ~3 min |

**Total full CI ~4 min, pre-commit ~1 min** (L1 + L3 + L4 fast subset).

### 8.1 L1 — Replay determinism

Two fast-mode runs of the same script must produce byte-identical parity output:

```bash
godot --headless ... --script credits.txt --out a.txt
godot --headless ... --script credits.txt --out b.txt
diff -q a.txt b.txt   # must be empty
```

Defends against: AI cached outputs / test-mode-detection special-casing.

### 8.2 L2a — Script parity vs C

8 scripts: 6 visible to AI sessions, 2 held-out. Each runs in fast Godot, captures parity output, compared to committed C goldens via tolerance comparator.

Defends against: input handling errors, menu state machine errors, dialog dispatcher bugs.

### 8.3 L2b — Demo parity vs C

9 demos extracted from FILE0001.GLB. Each loaded by Godot's `DemoPlayback` (overrides player position from records), runs the corresponding wave's enemy AI with seeded RNG, captures parity output, compared to C goldens.

Defends against: enemy AI errors, scoring errors, collision errors, spawn timing errors.

### 8.4 L3 — Property invariants

Free assertions during L2 runs. Listed in §11 (Properties). Failure = test failure.

Defends against: bounds violations, state-machine corruption, save-load drift.

### 8.5 L4 — Seed sweep

100 baseline runs of `mission_start` with seeds 0–99. To get 100 distinct deterministic runs out of a game whose only `srand()` call is `srand(1024 * wave_num)`, both implementations honor a `RAPTOR_RNG_SEED_OVERRIDE=N` env var that, when set, replaces the per-wave seed value. C-side change: ~3 lines in `RAP.C`. Godot-side: matching check before `WaveController.Rng.Seed = …`.

Goldens for all 100 seeds committed as `tests/parity/seeds/seed_<N>.parity.txt`. CI runs Godot with each seed, compares per-checkpoint with same tolerances as L2.

Defends against: AI overfitting to one specific seed; RNG handling bugs that only show under different seed sequences.

### 8.6 L7 — AI visual diff

For each script in L2a, extract 5 checkpoint frames as PNG screenshots from C side and from Godot side. Send each pair to Codex with this prompt:

```
Two frames from a top-down vertical-scrolling shoot-em-up.
Frame A is from the 1992 original. Frame B is a 2026 reimplementation.
Visual style is allowed to differ; new colors, smoother sprites,
modernized HUD layout are all expected and fine.

Flag DIFFERENT only if there is a meaningful gameplay-state mismatch:
- wrong number of enemies on screen (off by more than 2)
- player ship in wildly different location (>30% screen apart)
- missing major HUD element (no shield bar, no score)
- missing game world (one is black/empty, the other is not)

Reply EXACTLY this format:
  VERDICT: SAME | DIFFERENT
  REASON: one short line
```

Run each pair through 3 calls; majority vote determines verdict. Pass: ≥90% of pairs return SAME majority.

Defends against: rendering bugs not visible in numerics (e.g., wrong sprite assigned, HUD position broken, tile inversion).

## 9. Held-out scripts policy

`tests/scripts/holdout/` contains 2 scripts the AI agent sessions must not read. Enforcement:

1. The directory is listed in `CLAUDE.md`'s "do not read" section.
2. `.claude/settings.json` denies Read on `tests/scripts/holdout/**`.
3. CI runs L2a against both visible scripts AND held-out scripts. Held-out goldens are in `tests/parity/scripts/holdout/`, which CI can read but AI dev sessions cannot.
4. If held-out scripts pass throughout development but then fail one specific commit, that's a strong signal of overfitting.

Held-out scripts are regenerated annually (or whenever the visible set is materially extended) by a human running `dosraptor`'s capture script.

### 10.3 Citation: language choice rationale

C# over GDScript per [godogen's documented analysis](https://github.com/htdt/godogen/blob/master/docs/gdscript-vs-csharp.md):

- GDScript's `:=` type inference fails silently on common patterns (`load()`, `instantiate()`, array access).
- C# compiler catches type errors before runtime.
- LLM-generated C# requires fewer iteration cycles than GDScript.

Cited verbatim in `CLAUDE.md` to prevent re-litigation per session.

### 10.4 Explicitly not installed

- Game Studios framework (49 agents, too heavy for project size).
- hi-godot/godot-ai (overlaps with Coding-Solo, less popular).
- godot-mcp-pro (paid, no advantage we need).

## 11. Properties / invariants

The structural contracts the design enforces. Each is unambiguous, testable, and bounded to a clear domain.

| Name | Statement | Domain |
|---|---|---|
| **Sim determinism** | Same script + same seed → bit-identical parity output, byte-for-byte | Any Godot test-mode session (L1) |
| **Reproducibility** | `golden_capture` run twice on same script produces byte-identical output | C-side capture pipeline; verified by `golden_capture.sh` running twice |
| **Tick-only motion** | `src/Sim/**` files contain no reference to `delta`, `_process`, `Time.*`, `OS.GetTicks*`, or `GD.Rand*` outside whitelisted sites | Sim layer; CI-enforced by `lint_sim.sh` |
| **State bounds** | At every checkpoint: `0 ≤ player_x ≤ 319`, `0 ≤ player_y ≤ 199`, `0 ≤ shield ≤ 100`, `0 ≤ enemies ≤ 64`, `score ≥ 0` | Every parity checkpoint emitted by either binary (L3) |
| **Frame monotonicity** | `fc` is strictly increasing within a session (no resets, no decreases) | Per-checkpoint sequence (L3) |
| **Score monotonicity (within mission)** | `score` is non-decreasing between consecutive checkpoints while `win == MISSION_*` | Per-checkpoint sequence; resets allowed across menu transitions (L3) |
| **Save round-trip** | `save → load → save = save` (byte-equal) | Save subsystem; tested with explicit round-trip test |
| **Oracle equivalence (parity)** | Godot output checkpoints satisfy tolerances vs committed C goldens at ≥95% of checkpoints | L2a / L2b / L4 comparator |
| **Schema conformance** | Every parity checkpoint line conforms to `tests/parity/schema.json` | Both C and Godot parity emitters; validated in CI |
| **Held-out integrity** | No file under `tests/scripts/holdout/` is read by AI dev sessions | Repo policy (CLAUDE.md), `.claude/settings.json` deny rule, audit log |
| **Visual style independence** | Vision-model prompt instructs to ignore palette/sprite-art; only flags structural mismatch | L7 prompt + sample evaluation log |
| **Replay equivalence** | Two consecutive fast-mode runs of the same script produce byte-identical parity output | Godot replay test (L1) |
| **No external time dependence** | No sim file reads wall-clock; all timing through `SimClock.Frame` | `lint_sim.sh` |
| **Single-RNG-per-wave** | Every `random()` call in sim goes through `WaveController.Rng` | Code review + lint |

## 12. What we explicitly chose NOT to do

| Rejected option | Why |
|---|---|
| **Pattern A: headless sim core in pure C# class library** | The looser tolerances (±8 px, ±15% score) make idiomatic Node2D entities safe. Pattern A's value (strict byte-parity) is paid for in ~1500 lines of duplication and the un-Godot-idiomatic structure. Reconsider only if L1 proves flaky under idiomatic Godot. |
| **Pattern C: hybrid sim records + node mirrors** | Two parallel state collections invite drift. The discipline cost approaches Pattern A without Pattern A's clean separation. |
| **libc rand() port to C#** | Tolerances absorb RNG drift between systems. Per-wave seeded `RandomNumberGenerator` is fully deterministic *within* the Godot binary, which is what L1 requires. |
| **Custom AABB collision** | `Area2D` is sufficient; collision-order nondeterminism would surface as L1 failures and can be fixed locally if it appears. |
| **Custom game loop replacing scene tree update order** | Scene tree order is stable per binary. L1 catches any nondeterminism. |
| **Strict pixel-hash parity vs C version** | Defeats the purpose of using a different engine. Replaced by L7 (AI visual diff) for "looks right" + L2 (numeric parity) for "behaves right". |
| **Random-input fuzz layer (L6)** | Held-out scripts cover the same defense (test-mode-detection) more cheaply and with realistic gameplay scenarios. |
| **Statistical signatures (the OLD L4)** | Original C version is fully deterministic per wave seed; no natural distribution to compare against. Replaced by seed-sweep L4 — same name, different mechanism. |
| **Game Studios 49-agent framework** | Overkill for project size. Specific skills (e.g., `/code-review`) can be cherry-picked later. |
| **GLB runtime reader in C#** | One-shot extraction is ~500 lines simpler. No phase-1 use case for runtime asset modification. |
| **Cross-version save compatibility with C original** | Out of scope. Saves are local to this build. |
| **Maintaining a single repo for both implementations** | Different toolchains (cmake/SDL vs Godot/.NET) and CI flows. New repo keeps each clean. |

## 13. Phase 1 done definition

Phase 1 is complete when:

1. `raptor-godot` repo exists with the structure in §2.1.
2. All committed assets in `assets/` extracted from FILE0001.GLB and committed.
3. The Godot binary launches, plays the intro, reaches the main menu, and runs every script under `tests/scripts/` (visible and held-out) to completion without crashing.
4. **L1 passes** (replay determinism on at least 1 short script).
5. **L2a passes** at ≥95% of checkpoints across all 6 visible scripts AND the 2 held-out scripts.
6. **L2b passes** at ≥95% of checkpoints across all 9 demos.
7. **L3 invariants hold** across all L2 runs.
8. **L4 passes** at ≥95% of checkpoints across all 100 seeds.
9. **L7 passes** at ≥90% SAME verdicts across the 50-pair set.
10. CI runs full L1+L2+L3+L4+L7 in <10 minutes on M-series Mac.

Phase 1 is **not** complete just because the game appears to work. Phase 1 is "the suite goes green and stays green."

## Appendix A — Definitions

- **Tick**: one iteration of `_PhysicsProcess`. 1/70 of a logical second.
- **Frame** (in this doc): equivalent to tick; named for compatibility with the C version's `framecount`.
- **Sim**: code under `src/Sim/` and `src/UI/` whose execution affects parity output.
- **View**: code under `src/View/` whose execution does not affect parity output.
- **Checkpoint**: a parity output line emitted every 70 ticks (1 second).
- **Golden**: a committed parity output file generated from the C version, treated as ground truth.
- **Held-out**: a script or golden the AI dev session is denied access to.
